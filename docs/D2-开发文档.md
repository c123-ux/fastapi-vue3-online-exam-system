## 2. 架构设计

### 2.1 分层架构

```
┌────────────────────────────────────────────────────────────┐
│  API 层  routers/ （auth/questions/papers/exams/stats）     │
│  Pydantic 校验(schemas) + 角色依赖(security) + 异常翻译      │
├────────────────────────────────────────────────────────────┤
│  Service 层 services/                                      │
│  question/paper/exam/grade/stats + 闸门/清算/限时/防重      │
├────────────────────────────────────────────────────────────┤
│  models.py(SQLAlchemy) database.py  security.py  redis_client.py│
│  time_utils.py(单点时钟)  exceptions.py(统一错误)            │
├──────────────────────────────┬─────────────────────────────┤
│  MySQL 8.0.46  127.0.0.1:3307│  Redis 5.0.14.1 原生 D:\Redis│
│  exam_db(dev) exam_test(test)│  db0=dev db1=test           │
│  （事实源）                   │  （判活/倒计时/提交标记）      │
└──────────────────────────────┴─────────────────────────────┘
```

原则：routers 只做校验与调用；判分/限时/防重/清算全部收敛在 services；判分引擎是**脱库纯函数**（dataclass 入参，C8）。

### 2.2 考试主链路（正常交卷）

```
学生                Service                          MySQL                    Redis
 │ POST /exams/{paper_id}/start                                     │
 │────────────────►│ 分支①无记录: 校验 published+时间窗(EC-01~04)      │
 │                 │  建 record: deadline_at=min(now+duration,end_at) │
 │                 │  写 snapshot_json(题集+分值+正确答案) ──────────► │
 │                 │  SET exam:session:{rid} <json> EX ttl ◄─────────│ 原子带 TTL
 │                 │ 分支②有记录且未交: 禁改 deadline_at(EC-09)        │
 │                 │  session 缺失→按剩余重建(ttl≤0→转清算 EC-09)      │
 │                 │ 分支③已交卷: 409 ALREADY_SUBMITTED(EC-10)        │
 │◄─{record_id, 快照(无答案), remaining}────────────────────────    │
 │                                                                     │
 │ POST /exams/{rid}/answer {question_id, answer}                      │
 │────────────────►│ SELECT record FOR UPDATE（与提交/清算串行）        │
 │                 │ 校验: status=in_progress 且 now≤deadline+grace    │
 │                 │      （超期→409 EXAM_TIME_UP 并触发清算 EC-11）     │
 │                 │ upsert answers 落库 ────────────────────────────►│
 │                                                                     │
 │ POST /exams/{rid}/submit                                            │
 │────────────────►│ 1.归属/状态预检（非 in_progress→409）              │
 │                 │ 2.时间判定（DB 权威: now>deadline+grace→超时分支） │
 │                 │ 3.Redis SETNX 存在预检（快速 409，仅优化） ◄───────│
 │                 │ 4.条件 UPDATE 抢闸: WHERE id=:rid AND             │
 │                 │   status='in_progress'（rowcount==1 才有权判分）   │
 │                 │ 5.事务内判分: 快照为基准→客观题判/未答补 0/         │
 │                 │   未答简答 skipped/已答简答 pending                │
 │                 │ 6.commit（失败→回滚，标记未置，学生可重试）         │
 │                 │ 7.SET exam:submit:{rid} EX 86400（commit 后才置）◄│
 │◄─{status:"final", submit_kind, earned_score, full_score, pending} │
```

### 2.3 超时链路（惰性清算）

```
场景 A：超时后学生主动提交 → §2.2 第 2 步判定超时 → 条件 UPDATE 抢闸 → 判分 → submit_kind=timeout
场景 B：超时后学生再未访问 → 读路径触发 reap（学生查成绩 / 老师 results/stats / 同卷 start）：
  SELECT record → now > deadline_at + grace？
    → UPDATE ... SET status='final', submit_kind='timeout', ...
         WHERE id=:rid AND status='in_progress'   ← 与场景 A/并发 reap 同一闸门
    → rowcount==1 才判分落库；rowcount==0 说明别人已清算，直接返回
  为什么不用 keyspace notification（修正 v1.0 的错误理由）：
    Redis 5.0 支持过期事件【实测开关可设】，但需要常驻订阅、事件不保证送达、
    Redis 重启丢失、TestClient 里难测——成本与不可靠性都高于「读时清算 + 答案实时落库」。
```

### 2.4 Redis 与数据库的一致性约定（v1.1 强化）
- **DB 是事实源**：`deadline_at` 开考时一次写入、永不更新；Redis TTL 只负责判活与倒计时派生。
- **TTL 命令语义表**（实测）：存在且有过期 → 正整数；**存在无过期 → -1（异常态：按 DB deadline 立即重设，绝不当作"会话存在"）**；不存在 → -2（走重建/超时判定）。
- **负 TTL 两条路径**（实测）：`EXPIRE` 负值=静默删键、`SET EX` 负值=抛异常 → 统一 `ttl = max(1, int(deadline_at + grace - now))`，且 **ttl ≤ 0 时不进重建分支，直接走超时判定**。
- **判定权威**：交卷/作答的时间判定以 DB（deadline_at + 单点时钟）为准；Redis 存在性只用于快速失败与剩余时间展示。此为对需求文档「以 Redis TTL 为准」的有意偏离（见 §10 偏离表 #2）。
- **Redis 标记丢失不影响正确性**：提交标记、会话均可由 DB 状态重建；Redis 只是优化层。

### 2.5 状态机转移表（B1 修复的核心；D3 按此表逐条出用例）

字段：`status`(in_progress|final) × `submit_kind`(NULL|normal|timeout) × `review_state`(NULL|pending|final)

| # | 当前状态 | 事件 | 守卫条件 | 动作 | 次状态 |
|---|---|---|---|---|---|
| T1 | 无记录 | POST start | paper=published 且 start_at≤now≤end_at | 建 record（deadline=min(now+duration, end_at)，写 snapshot_json）+ SET 会话 | in_progress |
| T2 | in_progress | POST start（幂等续考） | 同 T1 时间窗；未交卷 | **禁改 deadline_at**；会话缺失且 ttl>0 才重建；返回快照+remaining | in_progress（不变） |
| T3 | in_progress | POST start | 记录已交卷（status=final） | — | 409 `ALREADY_SUBMITTED` |
| T4 | in_progress | POST answer | FOR UPDATE 后：in_progress 且 now≤deadline+grace 且题∈快照 | upsert answers | in_progress |
| T5 | in_progress | POST answer 超期 | now>deadline+grace | 先触发 T8 清算 | 409 `EXAM_TIME_UP` |
| T6 | in_progress | POST submit（宽限内） | 条件 UPDATE 抢闸成功 | 判分落库（快照基准），submitted_at=now | final + submit_kind=normal + review_state=pending（有已答简答）或 final（无） |
| T7 | in_progress | POST submit 超期 | now>deadline+grace 且抢闸成功 | 同 T6 判分 | final + submit_kind=timeout |
| T8 | in_progress | 惰性清算（读路径） | now>deadline+grace 且抢闸成功（WHERE status='in_progress'） | 同 T6 判分，WARNING 日志 | final + submit_kind=timeout |
| T9 | final(review_state=pending) | POST review | 创建者；题=short；0≤score≤卷面分值；FOR UPDATE | 更新 answer(score / review_status=`reviewed` / comment)；原子重算 earned_score；无 needs_review → 定稿 | final + review_state=final |
| T10 | final | start / answer / submit | — | — | 409 |
| T11 | in_progress | cheat-report | 本人且 in_progress | `UPDATE ... SET cheat_count=cheat_count+1`（DB 直写，无 Redis 键） | in_progress |
| T12 | 任意 | 读路径命中 in_progress 且未过期 | — | — | 不变（不误清算） |

> 判分补齐规则（T6/T7/T8 共用）：全卷每题都有 answers 行——未答客观题 is_correct=false/score=0；未答简答 review_status=`skipped`/score=0；已答简答 review_status=`needs_review`/score=NULL。
> 术语约定（v1.2，N4）：`snapshot_json` 一律称**判分基线**（内含正确答案，永不出现在任何响应里）；`GET /api/exams/{record_id}` 的返回称**续考响应**（不含答案）。两者不是同一个东西。

| id | BIGINT | PK | |

## 5. 关键接口设计

### 5.1 统一约定（v1.1 强化）
- 错误统一体 `{code, message, detail}`：**code=英文短码（如 ALREADY_SUBMITTED），message=英文短语，detail=中文可读说明**；`main.py` 注册 `AppError` 与 `RequestValidationError` 两个 handler，**422 也渲染成统一体**（否则 D3 按 422 断言默认 FastAPI 结构必红，B19）。
- 状态码：400 业务规则 / 401 未认证 / 403 角色不符或注册码错误 / 404 不存在或跨用户资源（存在性隐藏）/ 409 重复提交与状态冲突 / 422 结构校验（**含路径参数类型不合**，如 `/api/exams/abc` → 422 int_parsing，实测）/ 500 依赖或服务异常。
- **权限判定顺序固定**：401 → 403 → 404 → 400/409（D1 §2.2）。同一条 404 对"资源不存在"与"存在但不归属"返回**完全相同的 code/message**。
- 认证：`Authorization: Bearer <JWT>`；claims：sub/role/exp（240 分钟，B8）。

### 5.4 响应白名单与泄露防线（v1.2 新增，N4）
- 每个接口的响应都用 `schemas.py` 里的**显式字段白名单模型**；**禁止** `XxxOut.model_validate(orm_obj)` 直出 `exam_records`（该表含 `snapshot_json` → 直出即把正确答案发给学生）。
- 判分基线只在 service 内部消费；`exam_records` 对外一律经 `ExamRecordBrief` / `ScoreOut` / `ResumeOut` 三个白名单视图。
- 自动化防线：`tests/integration/test_no_leak.py` 以学生身份遍历全部 GET/POST 端点，断言响应正文不含子串 `correct_answer`、`reference_answer`、`snapshot`（写进 DoD）。

### 5.5 路由声明顺序（v1.2 新增，N2）
- **字面量路径必须先于同层参数路径注册**：实测（fastapi 0.116.1 / starlette 0.47.3）若 `/api/exams/{record_id}` 先声明，`GET /api/exams/my` 返回 **422**（`record_id` 的 int 解析失败），字面量 handler 永远不可达——Starlette 只按路径模板匹配，类型转换在匹配之后，**不会回退**。
- 因此「我的考试记录列表」定名 **`GET /api/exams`**（段数不同，天然无冲突）。
- `include_router` 顺序写进代码规范：auth → questions → papers → exams → stats；`exams.py` 内部按「无参数段路由在前」排列。
- S6 自验必须同时断言 `GET /api/exams` 与 `GET /api/exams/{record_id}` 可达（防回归）。

## 6. 关键数据结构与算法

### 6.1 判分引擎（grade_svc，脱库纯函数，C8）
- 入参 dataclass：`QuestionSpec(id, type, correct_answer, full_score)` / `AnswerSpec(question_id, student_answer, answered: bool)` / 输出 `GradeResult(is_correct, score, review_status)`——TC-U-01~05 不碰 MySQL/Redis；service 层负责 DB/快照 → dataclass 适配。
- 规则表：
| 题型 | correct_answer 存储 | 学生答案规范化 | 判分 |
|---|---|---|---|
| single | `"A"` | strip/upper | 严格相等 |
| judge | `"T"/"F"` | true/false/对/错 → T/F | 严格相等 |
| multiple | `"A,C"`（排序逗号分隔） | 数组→去重/upper/排序/join | **集合全等**；少选/错选/多选 0 分 |
| short | 允许空串（参考答案仅展示） | 原文 ≤1000（超限 422） | **不自动判**：已答→pending；未答→skipped 0 分 |
- 补齐：判分循环覆盖快照全卷（未答客观 is_correct=false/0；未答简答 skipped/0）。
- 聚合：`auto_score=Σ客观分`；`earned_score=auto_score+Σ已批简答分`；`pending_review_count=Σ(review_status='pending')`；pending=0 → review_state=final。

### 6.2 Redis key 规范（v1.1 重写）
| Key | 类型 | 写法 | TTL |
|---|---|---|---|
| `exam:session:{rid}` | **String(JSON)**：`{record_id, started_at, deadline_at, grace_seconds, duration_minutes}` | **`SET key <json> EX <ttl>` 原子带 TTL**（禁 Hash——实测 HSET 后 TTL=-1 永不过期，A3） | `max(1, int(deadline_at+grace−now))`；≤0 不写，直接走超时判定 |
| `exam:submit:{rid}` | String | **commit 成功后** `SET key <ts> EX 86400`；前置 `EXISTS` 仅作快速 409 | 86400；丢失不影响正确性（B3） |
| ~~`cheat:{rid}`~~ | — | **删除该键**（v1.0 设计）：计数只写 DB，Redis 重启不漂移（B14） | — |
| `paper:cache:{paper_id}` / `ratelimit:{ip}` | — | P1 预留不实现；**若将来实现，任何 INCR 建键必须显式 EXPIRE**（实测 INCR 键 TTL=-1） | — |

异常面（v1.2 补 `protocol=2`）：`redis_client.py` 统一 `Redis(..., protocol=2, socket_connect_timeout=1, socket_timeout=1, health_check_interval=30)`，捕获 `redis.exceptions.RedisError`（含 TimeoutError），转 500 + ERROR 日志（B18）。**`protocol=2` 不是可选项**：本机 Redis 5.0.14.1 不认 `HELLO`，redis-py 走 RESP3 会在连接阶段抛 `unknown command 'HELLO'`（实测，N1）。测试用 db1，conftest 只 `flushdb` db1、**禁止 flushall**（C7）。

### 6.3 限时算法（v1.1）
1. T1 开考：先校验窗口下限 `end_at − now ≥ min(60s, duration×60×10%)`，否则 400 `EXAM_WINDOW_TOO_SHORT`（EC-31）；`deadline_at = min(now + duration_minutes×60, end_at)`（B7 窗口截断）落 DB；`ttl = max(1, int(deadline_at + grace − now))`；`SET exam:session:{rid} <json> EX ttl`。
2. 剩余时间下发（v1.2 改）：**`remaining_seconds = max(0, int((deadline_at − now).total_seconds()))`，纯 DB 计算，不查 Redis**（N5：正常态与「TTL − grace」数值等价，但 Redis 不可用时读路径仍成立，符合 NFR-08）；幂等 start **禁改 deadline_at**（A7），连续 start remaining 单调不增。
3. 会话缺失（TTL=-2）：`ttl = int(deadline_at + grace − now)`；**ttl ≤ 0 → 不重建，走超时判定**（负 EXPIRE 会静默删键、负 SET EX 会抛异常——两条路径都堵死，A3(c)）。
4. `TTL` 返回 **-1**（存在无过期，实测 Hash/漏 EXPIRE 场景）：视为异常态，立即按 DB deadline `EXPIRE` 重设，**不得当作会话有效**（A3(b)，配专测）。
5. 交卷/作答时间判定以 DB 为准：`now > deadline_at + grace` → 超时分支（即使 Redis 会话仍在——防漏 EXPIRE 时无限续考）。
6. 所有时间取自 `time_utils.now()` 单点（B20）；`DATETIME(3)` 消除秒级截断。

### 6.4 防重复提交与并发闸门（v1.1 重写，B2/B3）
**权威 = DB 条件更新；Redis = 优化**。提交/清算统一时序：
1. 归属与状态预检（非 in_progress → 409，携带首次信息）；
2. 时间判定（DB 权威，§6.3.5）；
3. Redis `EXISTS exam:submit:{rid}` 预检 → 命中快速 409（双击优化，**不作为正确性依据**）；
4. **条件 UPDATE 抢闸**：`UPDATE exam_records SET status='final', submit_kind=:kind, submitted_at=:now ... WHERE id=:rid AND status='in_progress'` → `rowcount==1` 才拥有判分权（InnoDB 行锁串行化并发提交/并发清算/批改竞争）；
5. 事务内判分落库（快照基准）→ commit；**失败回滚 → 标记未置、状态未变，学生可重试**（B3 的锁死场景从根上消除）；
6. commit 后 `SET exam:submit:{rid} EX 86400`（仅幂等提示用）。
批改/作答走 **`SELECT ... FOR UPDATE` record 行**后读写（读-改-写原子，B11）；两条闸门按路径适配（D1 附录 B-18）。

### 6.5 惰性清算（v1.2 补事务边界）
触发点：学生查成绩 / 老师 results / stats / 同卷 start。条件：`status='in_progress' AND now > deadline_at + grace`；动作：§6.4 抢闸 → 判分 → `submit_kind='timeout'`，WARNING 日志；**清算结果与其他交卷一样进入统计与批改流**（B1 修复）。
**事务边界（N10）**：一次读路径要清算多条时，**逐条独立事务**（每条各自抢闸+判分+commit），单条失败只记 ERROR、不阻断整个响应；响应里以 `reaped_count` 回报本次清算条数。不做"整批一个事务"——一条脏数据会连带让其余 39 人的成绩不显示。
**时间比较一律在 Python 侧用 `time_utils.now()`**（N9/N13）：SQL 里不得出现 `NOW()`/`CURRENT_TIMESTAMP`（含 `server_default`），否则测试注入的假时间不生效、超时用例退化成"真等 600 秒"。候选集用 `WHERE status='in_progress'` 取回后在应用层比时间（本项目量级足够）。
不选 keyspace notification 的理由（修正措辞）：能力存在【实测 5.0 可开】，但需常驻订阅、事件不保证送达、Redis 重启丢失、TestClient 难测；「读时清算 + 答案实时落库」成本最低且逻辑可单测。

### 6.6 组卷与判分基准保护（B6）
- 手动组卷：校验（存在/分值>0/不重复）→ 批量插入 → full_score 求和；随机抽题 P1 预留：先 `SELECT id`（按 category/type/difficulty）→ Python `random.sample` → `WHERE id IN`，避免 `ORDER BY RAND()`。
- **锁定**：题目被 published/closed 卷引用后，content/options_json/correct_answer/type 修改 → 409 `QUESTION_LOCKED`（category/difficulty 不参与判分可改）；删除 → 409 `QUESTION_IN_USE`。
- **判分基线**：T1 开考把 `{question_id, type, content, options, correct_answer, score, sort_order}` 写入 `exam_records.snapshot_json`；**判分与批改只读它**，与当前题库解耦——迟到的清算不会用"改后的答案"判分。
- **统计与卷面展示读 `paper_questions` + `questions`（v1.2 写死，N6）**：判分基线是"每人一份 JSON"，无法跨记录聚合；因锁定规则（published 后题集/分值/答案不可变），二者恒等。本期**不提供 `PUT /api/papers` 与 `DELETE /api/papers`**——没有接口就没有后门。

### 6.7 统计实现要点（B12）
- SQL 遵守 `ONLY_FULL_GROUP_BY`：SELECT 中非聚合列全部进 GROUP BY（SQLite 不报、MySQL 报——必须在真库测）；
- `correct_rate` 分母（已交卷记录数）为 0 时返回 0，防 `ERROR_FOR_DIVISION_BY_ZERO`；
- 均分两级口径见 §5.3 stats 示例：**每个均值必须与自己的样本数成对回报**（`avg_score`+`avg_scored_count`、`avg_auto_score`+`finished_count`），timeout_count / reaped_count 单列；
- 判分依据取自记录判分基线，**聚合的题面与满分取自 `paper_questions`**（§6.6）。
